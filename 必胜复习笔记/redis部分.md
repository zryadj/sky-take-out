# 1.缓存问题

### 缓存穿透、缓存击穿、缓存雪崩的本质区别

这三者都是缓存问题，但发生的原因和后果不同。理解它们的区别有助于你更好地设计缓存策略。

1. **缓存穿透 (Cache Penetration)** （无数据 0）
   **本质**：指的是查询一个不存在的数据，缓存中没有，数据库中也没有。每次请求都会查询数据库，造成对数据库的压力。
   **原因**：请求的数据在缓存中不存在，也不在数据库中，通常是恶意请求或参数错误的请求导致的。 **防范方法**：

   - **参数校验**：对请求参数进行严格校验，避免不合法的请求。
   
   - **空值缓存**：对于查询不到的数据，可以缓存空值（设置短时间 TTL），避免每次都查询数据库。
   
   - ###### 布隆过滤器
   
     **速记**：请求不存在的数据，缓存没有，数据库也没有。

### **计数布隆过滤器实现（Redisson + Redis）**

Redisson **默认不支持计数布隆过滤器**，但可以使用 **Redis 的 Hash 结构** 来模拟。

- 采用 **Redis Hash 结构** 存储计数器：`CF:filter_name`

- **新增元素**：将 `key` 计算出的多个索引位置的计数器 `+1`。

- **查询元素**：检查多个索引位置的计数器是否都大于 0。

- **删除元素**：多个索引位置的计数器 `-1`，并在 `0` 时清除。

  

  **缓存击穿 (Cache Breakdown)**  （一个数据 多个请求）

  **本质**：指的是某一时刻缓存中的某个热点数据过期，多个请求同时发起，导致多个请求同时查询数据库，造成数据库压力骤增。
  **原因**：某个缓存数据过期，并且有大量并发请求同时访问这个数据，导致缓存没有及时命中，数据库压力增加。 **防范方法**：

- **互斥锁**：在缓存失效时，使用分布式锁（如 Redis 的 `SETNX` 或 `Redisson`）来保证只有一个线程去查询数据库并更新缓存。
- **缓存预加载**：提前加载和更新热点数据的缓存。

- **使用redisson和逻辑过期结合，高并发，高可靠性，支持集群**



**速记**：热点数据缓存失效，多个请求同时打到数据库。

1. **缓存雪崩 (Cache Avalanche)**  （多个数据 多个请求 ）
   **本质**：指的是缓存中的大量数据同时过期，导致大量请求同时查询数据库，造成数据库压力过大，甚至崩溃。
   **原因**：缓存中的大量数据在同一时间过期，或缓存服务器宕机，导致所有请求都转到数据库。 **防范方法**：

   - **不同步过期**：设置不同的过期时间，避免大规模数据同时过期。
   - **缓存预热**：在缓存服务器启动时，预加载数据到缓存。
   - **分布式缓存**：使用分布式缓存集群，避免单点故障。

   **速记**：大量缓存数据同时过期，所有请求都打到数据库。

##### 实际项目中的真实案例

1. **缓存穿透案例**： 在一个电商项目中，有用户请求商品的详细信息，然而有些用户恶意请求不存在的商品 ID。由于没有有效的参数校验，缓存查询结果为空，并且每次都查询数据库，导致数据库受到了大量的无效请求压力。解决方案是：对商品 ID 进行合法性检查，且对于不存在的商品数据，在缓存中存储空值，设置短时间的缓存过期时间，避免缓存穿透。
2. **缓存击穿案例**： 在一个新闻推荐系统中，有一个热点新闻在某一时刻的访问量激增，缓存数据过期后，多个用户同时发起请求，导致数据库负载瞬间飙升。解决方案是：在缓存过期时使用分布式锁，保证只有一个请求去访问数据库并更新缓存，其它请求等待缓存更新完成后获取数据。
3. **缓存雪崩案例**： 在一个社交平台应用中，缓存中的大量用户数据同时在凌晨过期，导致大量用户请求同时打到数据库，造成数据库崩溃。解决方案是：设置不同的数据过期时间，避免缓存同时失效，并引入缓存预热机制，在缓存失效前就加载热门数据到缓存。



缓存击穿可能会伴随缓存穿透问题，穿透问题可增强校验逻辑 ，同时缓存空值，设置一个短暂的过期时间。

######  5.淘汰策略(内存不够,添加新key) 

​	8种:

​	 noeviction 默认不淘汰任何key

​	**🔹 适合缓存场景的淘汰策略**

| 策略             | 说明                                          | 适用场景                 |
| ---------------- | --------------------------------------------- | ------------------------ |
| **volatile-lru** | **淘汰最近最少使用（LRU）的**有过期时间的 Key | **适合短生命周期缓存**   |
| **allkeys-lru**  | 淘汰所有 Key 中的**最近最少使用（LRU）**      | **适合热点数据缓存**     |
| **volatile-lfu** | **淘汰使用最少的**有过期时间的 Key（LFU）     | **适合短期热点数据**     |
| **allkeys-lfu**  | 淘汰所有 Key 中**使用最少的**（LFU）          | **适合热点变化快的业务** |

​	**🔹 适合持久化数据的淘汰策略**

| 策略                   | 说明                                       | 适用场景                         |
| ---------------------- | ------------------------------------------ | -------------------------------- |
| **volatile-random**    | **随机淘汰**有过期时间的 Key               | **适合普通缓存**                 |
| **allkeys-random**     | **随机淘汰**所有 Key                       | **适合空间有限但无固定访问模式** |
| **volatile-ttl**       | **淘汰即将过期的 Key**（TTL 越小优先淘汰） | **适合临近过期的缓存**           |
| **noeviction（默认）** | **不淘汰，写入失败**                       | **适合数据必须保留的场景**       |

✅ **做缓存？用 LRU / LFU**

- 只缓存热点数据：`allkeys-lru`
- 只淘汰低频数据：`allkeys-lfu`

✅ **数据不可丢？用 noeviction**

- 适合持久化存储，如 **消息队列、持久数据**。

✅ **TTL 控制的缓存？用 volatile 规则**

- 适合有明确**过期时间**的缓存，如 **Session、Token**。

🔥 **最常用策略**：`allkeys-lru`（淘汰低频数据，保持热点）

💡 **速记口诀**：

- **LRU/LFU，热点数据先救助**（适合缓存）
- **TTL 随机有讲究**（适合定期过期数据）
- **noeviction，数据绝不动**（适合数据持久化）

LRU vs LFU 区别

| **策略**     | **LRU（Least Recently Used）**   | **LFU（Least Frequently Used）**   |
| ------------ | -------------------------------- | ---------------------------------- |
| **淘汰规则** | 淘汰**最近最少使用**的 Key       | 淘汰**使用次数最少**的 Key         |
| **衡量指标** | **最近一次访问时间**             | **访问次数**                       |
| **适用场景** | 热点数据有**短期访问特性**       | 热点数据有**长期访问特性**         |
| **优势**     | 适合**短期热点变化快**的场景     | 适合**长期热点稳定**的场景         |
| **劣势**     | 无法区分**长期低频但重要**的数据 | 需要额外维护**访问计数**，开销稍大 |
| **适合业务** | **网页缓存、短视频、社交热点**   | **数据库缓存、热门排行榜**         |
